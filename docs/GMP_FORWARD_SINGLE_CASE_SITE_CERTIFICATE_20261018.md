# Prospective GMP issuance — one originating Case, one Site, at most one certificate

**Owner decision: 18 October 2026.** This is the approved business rule for GMP certificates **newly issued through the inspection-Case workflow** from this change onward. It is a business event rule, not a condition inferred from document date or imported legacy ID.

- Every new GMP inspection Case has **one** canonical Site (`Case.site_id`). It may issue **zero or one** case-backed GMP Certificate. Zero is legitimate when issuance is refused or not yet performed.
- The GMP Certificate must refer to **that exact Case** and **the same canonical Site**; its grant scope belongs to that single Site. The new flow must not generate multi-Site GMP coverage.
- Reinspection/reassessment or replacement for the same reviewed `MÃ DC` creates a **distinct originating Case** and a **distinct new Certificate**. An older certificate's legal identity and immutable issued-version history remain accessible; the separate `CertificateRelationship.REPLACED_BY` relation is only populated from approved evidence, never inferred merely from a line code.
- A second `certificate.issue` operation on a Case already linked to any GMP Certificate is a **conflict (409)**, even when the old certificate is not currently flagged as the latest/current or is a legacy import. This is not resolved by changing `latest_flag`, editing a version or backdating the issue date.
- `CaseWorkflowService.issue_certificate` owns prospective validation. The PostgreSQL issuing transaction locks the Case before checking for an existing issued GMP Certificate; `get_case_certificate_issue_readiness` communicates the same domain guard. Neither attempts a correction of historical import data.
- GLP/GSP/GDP and other explicitly distinct GxP workflows keep existing business logic. Administrative/no-inspection Certificate issuance where no Case exists is a **separate pre-existing contract** and is **not changed or implicitly endorsed as a replacement for this GMP Case-based rule**. The data owner must approve any broader restriction separately.
- Existing legacy GMP 376 (Case 380 rather than 378) and GMP 1037/1180 (historical two-Site source certificates) remain **historical exceptions**, for which evidence-bound adjudication is required. This policy is not applied retroactively to delete, merge, or normalize them. The proposed multi-Site source-readiness check in Draft PR #31 is for historical review ONLY, not future GMP issue.
- The historic `gxp_legacy_rehearsal` dataset may include duplicate or contradictory `Certificate.case_id` references. Therefore do not add a blanket database unique constraint without a separate import/compatibility audit. App-level prospective issuance guard is fail-closed but does not alone make arbitrary SQL writers or imports safe. A future database-enforced prospective-only guarantee requires an approved additive strategy.

Acceptance tests include zero-cert eligibility, first GMP issuance PASS, second GMP from same Case denied before additional CertificateVersion/AuditEvent creation, same-Site GMP replacement **using a different Case**, Case/Site mismatch 422, no legacy-row mutation, and no adverse change to existing DDKD/promotion/other GxP behavior.

**Not authorized:** VM deploy or runtime changes, migration, real PostgreSQL writes, legacy Case FK relinking, certificate scope backfill, NAS/GCS, backup/restore or enabling the nightly backup timer. Source CI is not operational approval.
