## Source-bound trace — OBSERVED

1. HTTP middleware generates/echoes `X-Request-Id` for logging ([main.py:127](../backend/app/main.py#L127)); it does not impose uniqueness or propagate an operation receipt to the workflow.
2. `get_authenticated_user` verifies the configured identity; production resolves external identity through database-backed RBAC ([auth.py:368](../backend/app/auth.py#L368), ADR 0053). The route requires `change_request.edit` ([workflow router:438](../backend/app/api/routers/workflow.py#L438), [auth.py:78](../backend/app/auth.py#L78)). Current route permission is not evidence of per-Site access or permission to look up another user's receipt.
3. Pydantic `ChangeRequestCreateRequest` validates the create fields; it has no Case ID, operation ID or expected version ([read_models.py:1134](../backend/app/read_models.py#L1134)). The canonical parent here is the Site; do not infer a Case or create a multi-Site Case rule. Other partial-update endpoints use `model_fields_set`; omitted and explicit null must remain distinct where semantic.
4. `CaseWorkflowService.create_change_request` ([workflow.py:1722](../backend/app/services/workflow.py#L1722)) locks Site ([workflow.py:598](../backend/app/services/workflow.py#L598)), snapshots current affected certificates and eligibility artifacts ([workflow.py:1622](../backend/app/services/workflow.py#L1622)), then flushes ChangeRequest and links. ChangeRequest has a Site foreign key and legacy-ID uniqueness; affected-artifact uniqueness is per request/target, not a unique create-command identity ([phase1.py:1022](../backend/app/db/models/phase1.py#L1022), [phase1.py:1051](../backend/app/db/models/phase1.py#L1051)).
5. The audit helper flushes its event in the same Session ([workflow.py:732](../backend/app/services/workflow.py#L732)); the route commits before returning a validated result via `commit_or_409` ([session.py:16](../backend/app/api/session.py#L16)). An exception rolls back through the request Session dependency. `StaleDataError` maps to 409. A client losing the response loses the returned new IDs; no lookup by command exists.
6. An optional future command identity would need validation at the route/use-case boundary, server-derived actor and Site binding, and unique admission in the same database transaction before business effects. Receipt and audit must commit with the mutation; a mere request header or an audit search cannot enforce that invariant. This sentence is **INFERRED**, not an implemented contract.

## Identity options — RECOMMENDED_FOR_OWNER_APPROVAL

| Option | Safety and atomicity | Complexity, compatibility and failure modes |
| --- | --- | --- |
| A. Client-generated opaque random ID | One stable ID can be admitted by a unique constraint in the mutation transaction; server binds authenticated actor, Site, command and fingerprint. Same-ID/different-context must fail closed. | One request round trip and opt-in compatibility; ID recovery across reload needs a separately approved non-credential persistence design. A client can lose an ID or reuse it wrongly; admission/fencing still must be proved. Collision is improbable with an approved random format, never authorization. |
| B. Server-issued reservation | Server can acknowledge an identity before business work and coordinate status, subject to actor/current authorization. | Extra round trip and a committed reservation state require leases, stale reservations, crash recovery, abuse controls and retention. Reservation is not business commit; expiry cannot permit an old worker to commit without fencing. |
| C. Aggregate-scoped identity | Scope can bind command type, actor and aggregate, with unique database enforcement. | New Change Request has no ID until commit: Site is the existing owner, not a guessed Case. Scope design must prevent cross-Site/actor ambiguity and accidental duplicate logical intent; sharing an ID across scopes must not leak existence. Applies differently to other workflows. |

**Recommendation:** combine A's client-generated opaque ID with a server-enforced, actor/command/Site/payload binding as in C, initially only for opt-in Change Request creation. Prefer a globally unique operation key as the candidate admission constraint to avoid cross-scope reuse ambiguity, with no cross-principal disclosure; backend and security owners must decide scope and error semantics. B remains an alternative if durable in-progress visibility is required and its lifecycle cost is accepted. None supplies exactly-once effects without transaction, fencing, authorization and retention proofs.

## Candidate transaction and status model — INFERRED

A request is received at HTTP ingress but becomes an admitted contender only after server authentication, authorization and a unique operation-key insert in its database transaction. The Site lock and business write follow admission. Commit makes business, audit and receipt visible atomically; a crash before commit rolls them all back, subject to PostgreSQL's actual durability configuration, which has not been crash-tested here. A same-key contender blocks or receives a database timeout; on a committed conflict it must verify binding and only then use an authorized minimal outcome. No production timeout or retry behavior is chosen.

`COMMITTED` is defensible only for an authorized, committed receipt. A separately durable `REJECTED` needs its own semantics for authorization, validation and rollback. `IN_PROGRESS` requires a committed reservation plus lease/fencing and crash semantics; the tested uncommitted insert is invisible and provides no durable in-progress status. `NOT_FOUND` means only no visible authorized receipt at that instant; a prior request may still commit. `UNKNOWN` is a client interpretation for unresolved state, not a claim that the server has an outcome. Lookup racing commit and rollback, commit-ack loss and delayed admission must be tested in the real vertical slice.

## Frontend handoff and authorization gate

Before any implementation, agree whether and how a non-secret opaque operation ID and owner binding may persist across reload. A browser marker is only a lookup handle, not proof or permission; do not store bearer tokens, raw sensitive draft or cross-user data by default. Bind in-memory access generation to UI ownership only. Reauthenticate before lookup, verify current principal and Site/Case access through the approved server policy, and suppress late responses from old generations. Keep the write lock for an unknown command; editing a draft may continue without sending it. Preserve a reviewed version where the actual command has one; Change Request creation currently has none. Distinguish failed readback from failed mutation. Unlock or resend only under a specifically approved, proven receipt/fencing rule; never auto-resend on 401, 409, NOT_FOUND or timeout.

Google A→same A after renewal, A→B, revoked permissions, admin access, per-Site and per-Case access, non-enumerating 403/404 responses, browser restart, and all actual lookup behavior are **UNPROVEN**. There is no current outcome endpoint to test. An operation ID is not a capability. Prior frontend in-session guards and synthetic tests are not authenticated UAT or durable recovery.
